## Release notes

**crshhx v1.2.0 — Gold Series**

New:

- **Gold Series collection** in Pro Crosshairs, with its own category and a
  restrained gold label. Both designs are ordinary presets in the existing
  library: load one, edit it, save your own copy. The shipped design is never
  modified.
- **Arc Crown** — four segmented vermilion arcs (`#dc583e`) crowning a bright
  green centre point (`#28f953`), with the four cardinals left open so the
  centre of the screen stays clean for tracking.
- **Compact Mark** — a compact monochrome green cross (`#6af469`) with a hollow
  centre: the four inner edges form the aiming point. No outline, no dot.
- **Segmented-circle Designer controls** — segment count, arc span and pattern
  rotation, available to any ring-based design, not only to these two.

Improvements:

- The renderer draws **genuine SVG arcs** for segmented circles. Nothing is
  approximated with a dashed stroke or with rotated arms: what the preview
  draws is what the overlay draws.
- **Crosshair schema v3.** The three new fields are optional and default to a
  complete circle, so every configuration, saved setting and export file
  written by an earlier version loads unchanged and renders identically.
- Export files now stamp the version that wrote them, so an import can say
  where a library came from.

Both Gold Series designs are **fan recreations** measured from public reference
imagery of MrSavage's crosshair — geometry, not published settings. They are not
official presets and no endorsement is implied. This line ships in the
application and on the website next to both designs.

### Why the version test pins sources to each other, not to a literal

`tests/releaseVersion.test.ts` asserts that package.json, the lockfile root and
`APP_VERSION` **agree**, without hardcoding `1.2.0`, so the next bump needs no
edit to the test. It also asserts three things that are easy to break quietly:

- `electron-builder.yml` contains no version literal at all — both artefact
  names come from `${version}`. A hardcoded name here would keep shipping
  `…-1.2.0.exe` forever, and the website's download links would 404.
- `docs/release-notes/v${version}.md` exists, so a version cannot be bumped
  without writing its notes.
- The website's `releases.json` may **lag** the application but must never lead
  it: `latest` is compared against package.json, and every published artefact
  must carry its own version in both filename and URL, with a plausible size and
  a 64-hex digest. Advertising a build nobody can download is the failure this
  guards.

### Not verified, and not verifiable here

Stated plainly rather than implied by omission:

- **Both executables exist and their sizes and digests are verified, but nothing
  about the packaged application has been tested from here.** The `package` job
  ran green on `windows-latest` (run `42872910505`, manually dispatched on
  `main` at `59617ba`) and uploaded the artefact `crshhx-windows-main`. That
  run's log turned out to be readable from this sandbox after all, through the
  signed blob URL that `gh api repos/.../actions/jobs/<id>/logs` returns, even
  though `gh run view --log` fails here — so the figures quoted below come from
  the build itself. The artefact is still not downloadable from here, so not one
  byte of either executable was inspected, run, or hashed locally; the packaged
  metadata, the icon and the installer behaviour remain unverified from this
  side. What the sandbox cannot do at all also stands: no NSIS toolchain, and no
  `rcedit` on Linux to stamp the executables' icon and version metadata.
- **No overlay, DPI or display-scaling behaviour was exercised.** There is no
  Windows, no display server and no Electron binary in this environment
  (dependencies are installed with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`). OS
  scaling at 100 / 125 / 150 / 200 % is a checklist item for a real machine,
  not a claim.
- What *is* covered automatically: arc geometry against independently written
  trigonometry, identical geometry at application scale 1 / 1.25 / 1.5 / 2,
  legacy full-circle output unchanged, schema-v3 defaults and repairs, preset
  catalogue integrity, and `scaleFactor` handling against fake displays
  (including a non-finite value falling back to 1). Application *scale* is the
  crosshair setting; it is not OS display scaling, and the two are not
  conflated anywhere in this document.

## Applied: the website release metadata

`website/src/releases.json` now carries 1.2.0 and `latest` is `1.2.0`. Two
corrections to what this section said while the release was still prepared:

- **The entry goes at the END of `published`, not the front.**
  `website/tests/releases.test.ts` requires
  `published[published.length - 1].version === latest`, and `ChangelogPage`
  renders the array in order without reversing it, so the manifest is
  chronological — oldest first, newest last. Following this document's original
  instruction to insert at the front fails the website suite.
- **The published numbers are not the ones the packaging job printed.** See the
  next section: the artefact's bytes differ from that measurement, and it is the
  artefact's bytes that people download.

## Prepared, inert: the release-publish workflow

`.github/workflows/release-publish.yml` exists to publish a release from a
packaging run's artefact, and it still carries 1.1.0-specific text. It is
**not** modified in this branch, because changing a release workflow in the same
commit as a version bump makes the release harder to read, and because the
numbers in its body must be the measured ones. When publishing, either update it
or create the release directly; the changes it would need are:

- `inputs.run_id.default` → the `windows-release` run id for tag `v1.2.0`.
- `inputs.tag.default` → `v1.2.0`.
- The body text at lines 92–98 → the release notes above, with the two artefact
  names, their measured sizes and their SHA-256 digests.

`release-assets.yml` **did** need changing, twice, and this document's original
claim that it needed none was wrong in a way only publishing could reveal. It
still attaches exactly the two executables from the packaging run to whichever
release is published, prints their sizes and digests before upload, fails loudly
rather than duplicating assets, and never rebuilds or re-uploads anything by
hand — but it now also accepts a dispatched build of the tagged commit (PR #13),
and it can be dispatched against a release whose tag predates the current logic
(PR #14). The v1.1.0 release kept its assets throughout: both were re-read after
v1.2.0 was published and are unchanged.

### The measurement that disagreed, and which one is authoritative

The per-file sizes and SHA-256 were recovered from two independent places, and
the two do not agree.

The `package` job computed them with `Get-FileHash` and printed them:

    crshhx-crosshair-studio-portable-1.2.0.exe: 81,464,040 bytes  sha256=E93DAFF7D0C8F06B04768CE2046C271FAE85B193F67E0116CC201864541F839C
    crshhx-crosshair-studio-setup-1.2.0.exe: 88,863,594 bytes  sha256=68E8C0698D367107F50577576A57433DDB5360AA7905161785625266242426EC

Those lines were reachable after all, which corrects an earlier claim in this
document. `gh run view --log` fails here because the results-receiver CDN is not
routable from the sandbox, but `gh api repos/.../actions/jobs/<id>/logs` returns
a signed URL on `productionresultssa*.blob.core.windows.net`, and that host *is*
reachable. The same route recovers any past job log — the difference between
"the numbers exist but I cannot see them" and reading them.

The artefact's own bytes, as extracted and hashed by the attach job and as
stored by GitHub, are 1 and 4 bytes larger, with different digests:

    -rw-r--r-- 1 runner runner 81464041 … crshhx-crosshair-studio-portable-1.2.0.exe
    -rw-r--r-- 1 runner runner 88863598 … crshhx-crosshair-studio-setup-1.2.0.exe
    1b97d1878d1c44283496abdc633b20ed573c9264ee5edd2175d5e2aa8632fc19  artifacts/…setup-1.2.0.exe
    104309e1465437257e76268f9074a8968b24c8772d95cb40d5f959648e47264e  artifacts/…portable-1.2.0.exe

`sha256sum` on the runner and the `digest` GitHub reports for the stored asset
agree exactly — two measurements of the same bytes, in different places, at
different times. The outlier is the build-log reading, taken about half a second
after electron-builder's last line of output and about one second *before*
`upload-artifact` began reading the same two files. The files were still being
finalised when they were hashed.

**v1.1.0 is the control that makes this conclusion safe rather than
convenient.** Its build log measured 81,455,085 / `037476deef…8ba842e2` and
88,862,700 / `bed1e654a6…dccac45d`, and its published assets report precisely
those values. Same pipeline, same steps, exact agreement. So the transfer is
byte-faithful in general, and the v1.2.0 mismatch is a property of that
measurement moment rather than of the artefact.

The mechanism inside electron-builder was not determined and is not claimed
here. What is claimed is narrower and sufficient: the artefact's bytes are what
`upload-artifact` stored, what the attach job hashed and uploaded, what GitHub
stores as the release asset, and therefore what a visitor downloads. Those are
the values on the website. The build-log figures are recorded above rather than
deleted, because quietly discarding a disagreement is how a wrong checksum gets
published.

**Consequence for the packaging workflow.** The report step should not be quoted
as authoritative until it measures files that are final: re-measuring after
`upload-artifact`, or hashing the artefact's own contents, would make the
printed figures agree with what ships. That is a change to PowerShell which
cannot be tested in this sandbox, in the one job that must succeed, so it is
recorded here as a recommendation rather than made blind.

The ordering rule this section was written to explain still holds, and is now
satisfied: `releases.json` cannot be filled in before publication without
inventing numbers, and `tests/releaseVersion.test.ts` refuses a placeholder — it
requires a plausible byte size and a 64-hex digest for every published artefact.

       git fetch … +59617ba2c38e4680a63485d0b22062728035f92c:refs/tags/v1.2.0

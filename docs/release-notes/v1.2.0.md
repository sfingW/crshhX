## Release notes

**crshhx v1.2.0 — Gold Series**

New:

- **Gold Series collection** in Pro Crosshairs, with its own category and a
  restrained gold label. Both designs are ordinary presets in the existing
  library: load one, edit it, save your own copy. The shipped design is never
  modified.
- **Arc Crown** — four segmented vermilion arcs (`#dc583e`) crowning a bright
  green centre point (`#28f953`), with the four cardinals left open so the
  centre of the screen stays clean for tracking.
- **Compact Mark** — a compact monochrome green cross (`#6af469`) with a hollow
  centre: the four inner edges form the aiming point. No outline, no dot.
- **Segmented-circle Designer controls** — segment count, arc span and pattern
  rotation, available to any ring-based design, not only to these two.

Improvements:

- The renderer draws **genuine SVG arcs** for segmented circles. Nothing is
  approximated with a dashed stroke or with rotated arms: what the preview
  draws is what the overlay draws.
- **Crosshair schema v3.** The three new fields are optional and default to a
  complete circle, so every configuration, saved setting and export file
  written by an earlier version loads unchanged and renders identically.
- Export files now stamp the version that wrote them, so an import can say
  where a library came from.

Both Gold Series designs are **fan recreations** measured from public reference
imagery of MrSavage's crosshair — geometry, not published settings. They are not
official presets and no endorsement is implied. This line ships in the
application and on the website next to both designs.

### Why the version test pins sources to each other, not to a literal

`tests/releaseVersion.test.ts` asserts that package.json, the lockfile root and
`APP_VERSION` **agree**, without hardcoding `1.2.0`, so the next bump needs no
edit to the test. It also asserts three things that are easy to break quietly:

- `electron-builder.yml` contains no version literal at all — both artefact
  names come from `${version}`. A hardcoded name here would keep shipping
  `…-1.2.0.exe` forever, and the website's download links would 404.
- `docs/release-notes/v${version}.md` exists, so a version cannot be bumped
  without writing its notes.
- The website's `releases.json` may **lag** the application but must never lead
  it: `latest` is compared against package.json, and every published artefact
  must carry its own version in both filename and URL, with a plausible size and
  a 64-hex digest. Advertising a build nobody can download is the failure this
  guards.

### Not verified, and not verifiable here

Stated plainly rather than implied by omission:

- **Both executables now exist, but nothing about the packaged application has
  been tested from here.** The `package` job ran green on `windows-latest` (run
  `42872910505`, manually dispatched on `main` at `59617ba`) and uploaded the
  artefact `crshhx-windows-main`. This sandbox can neither download that artefact
  nor read that run's log — GitHub's artefact and log CDNs are unreachable from
  it — so the packaged metadata, the icon, the installer behaviour and the two
  executables' own sizes and digests are all unverified from this side. What the
  sandbox still cannot do at all also stands: no NSIS toolchain, and no `rcedit`
  on Linux to stamp the executables' icon and version metadata.
- **No overlay, DPI or display-scaling behaviour was exercised.** There is no
  Windows, no display server and no Electron binary in this environment
  (dependencies are installed with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`). OS
  scaling at 100 / 125 / 150 / 200 % is a checklist item for a real machine,
  not a claim.
- What *is* covered automatically: arc geometry against independently written
  trigonometry, identical geometry at application scale 1 / 1.25 / 1.5 / 2,
  legacy full-circle output unchanged, schema-v3 defaults and repairs, preset
  catalogue integrity, and `scaleFactor` handling against fake displays
  (including a non-finite value falling back to 1). Application *scale* is the
  crosshair setting; it is not OS display scaling, and the two are not
  conflated anywhere in this document.

## Prepared, inert: the release-publish workflow

`.github/workflows/release-publish.yml` exists to publish a release from a
packaging run's artefact, and it still carries 1.1.0-specific text. It is
**not** modified in this branch, because changing a release workflow in the same
commit as a version bump makes the release harder to read, and because the
numbers in its body must be the measured ones. When publishing, either update it
or create the release directly; the changes it would need are:

- `inputs.run_id.default` → the `windows-release` run id for tag `v1.2.0`.
- `inputs.tag.default` → `v1.2.0`.
- The body text at lines 92–98 → the release notes above, with the two artefact
  names, their measured sizes and their SHA-256 digests.

`release-assets.yml` needs no change: it attaches exactly the two executables
from the packaging run to whichever release is published, prints their sizes and
digests before upload, fails loudly rather than duplicating assets, and never
rebuilds or re-uploads anything by hand. The v1.1.0 release keeps its assets.

`windows-release` run **42872910505** — `workflow_dispatch` on `main` at commit
`59617ba2c38e4680a63485d0b22062728035f92c`, both jobs green (*Tests, typechecks,
production build* 41s, *Windows installer + portable* 2m 43s) — uploaded one
artefact:

| | |
|---|---|
| Artefact | `crshhx-windows-main` |
| Contents | `release/*.exe`, uploaded with `if-no-files-found: error`, so both executables are present: `crshhx-crosshair-studio-setup-1.2.0.exe` and `crshhx-crosshair-studio-portable-1.2.0.exe` — the names follow `package.json`, which reads 1.2.0 at that commit |
| Artefact zip size | 170,328,720 bytes |
| Artefact zip digest | `sha256:6d461628cd5e82b7887bee7940e84699c150ba938e172f520a688385ea8f605d` |

**That digest is the zip's, not an executable's.** It must never be published as
either file's checksum: the artefact is a container holding both executables, and
quoting its digest would hand people a value that matches nothing they download.

The per-file sizes and SHA-256 do exist — the `package` job computed them with
`Get-FileHash` and printed them — but they are readable only from that run's log,
which sits on a CDN this sandbox cannot reach, and that job wrote no step
summary. So they are quoted **nowhere** in this document, and the website entry
above still carries its `MEASURED_*` placeholders. They become verifiable from
here the moment the release exists, because GitHub reports each release asset's
own size and `sha256:` digest through the ordinary API:

```
gh api repos/sfingW/crshhX/releases/tags/v1.2.0 --jq '.assets[] | {name, size, digest}'
```

That is the same call which, for v1.1.0, returns `88,862,700 /
bed1e654…dccac45d` and `81,455,085 / 037476de…8ba842e2` — exactly the figures
recorded in §20 of `docs/design/website-redesign.md`. The attach job also prints
`sha256sum` of the bytes it uploads, so the two sources can be cross-checked
before anything is published on the website.

**Ordering consequence:** `website/src/releases.json` cannot be filled in before
publication without inventing numbers, and `tests/releaseVersion.test.ts` refuses
a placeholder — it requires a plausible byte size and a 64-hex digest for every
published artefact. The website update is therefore a second, small change made
*after* the release exists, not part of this one.

## Publication steps — web interface only, each one needing approval

Nothing below has been done. None of it needs a local checkout or a terminal.

1. **Merge the workflow change** (the PR carrying this document). Until it is on
   `main`, `release-assets.yml` accepts only a tag-push build, so publishing
   first would produce a release with no assets and a failed attach job. Merging
   it also fires the bootstrap attach against the *latest* release — currently
   v1.1.0, which already carries its two assets — so that job reports "nothing to
   attach" and exits quietly. That is designed behaviour, not a failure.
2. **Draft the release:** repository → Releases → *Draft a new release* →
   *Choose a tag* → type `v1.2.0` → *Create new tag on publish* → set **Target**
   to `59617ba2c38e4680a63485d0b22062728035f92c`, the commit run 42872910505
   built. Title `crshhx v1.2.0 — Gold Series`, body from the release notes above,
   then **Publish release**.
   Targeting that exact commit is what lets the attach job reuse the build that
   already exists: it accepts a dispatched build only when the run's commit equals
   the tag's. Targeting `main` is equivalent *while main is still at `59617ba`* —
   but step 1 moves main, so after merging, target the commit explicitly.
   *If the tag does end up pointing somewhere else:* Actions → `windows-release` →
   *Run workflow* → branch `main` (about four minutes), then publish, or re-run
   the failed attach job from its run page. Still no terminal.
3. **Watch the attach:** Actions → *Attach release assets*. It resolves the tag to
   its commit (dereferencing an annotated tag), finds run 42872910505, confirms
   `crshhx-windows-main` exists and is unexpired, downloads it, asserts exactly
   the two `-1.2.0.exe` files and that neither is empty, prints `ls -l` and
   `sha256sum` of the bytes it is about to upload, and uploads them. If any check
   fails it fails without attaching anything partial, and it refuses outright if
   the release already carries assets.
4. **Verify the assets:** the release page must show both executables with their
   sizes, and the digests GitHub reports for them must match the attach log.
   v1.1.0's two assets must be untouched.
5. **Run the Windows checklist** (`v1.2.0-windows-verification.md`) on a real
   machine with both executables — the only evidence that the Gold Series works in
   the actual application, and nothing a sandbox can substitute for. Sections 1–3
   and 5–8 are the ones worth completing before announcing the release widely.
6. **Then the website:** a second, small change fills `releases.json` with the
   verified per-file numbers, sets `latest` to `1.2.0`, and deploys when merged.
   Only then does the download page describe what people can actually download,
   closing the gap where the live site already presents the Gold Series as
   installed while the newest published executable predates it.

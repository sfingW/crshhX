## Release notes

**crshhx v1.2.0 — Gold Series**

New:

- **Gold Series collection** in Pro Crosshairs, with its own category and a
  restrained gold label. Both designs are ordinary presets in the existing
  library: load one, edit it, save your own copy. The shipped design is never
  modified.
- **Arc Crown** — four segmented vermilion arcs (`#dc583e`) crowning a bright
  green centre point (`#28f953`), with the four cardinals left open so the
  centre of the screen stays clean for tracking.
- **Compact Mark** — a compact monochrome green cross (`#6af469`) with a hollow
  centre: the four inner edges form the aiming point. No outline, no dot.
- **Segmented-circle Designer controls** — segment count, arc span and pattern
  rotation, available to any ring-based design, not only to these two.

Improvements:

- The renderer draws **genuine SVG arcs** for segmented circles. Nothing is
  approximated with a dashed stroke or with rotated arms: what the preview
  draws is what the overlay draws.
- **Crosshair schema v3.** The three new fields are optional and default to a
  complete circle, so every configuration, saved setting and export file
  written by an earlier version loads unchanged and renders identically.
- Export files now stamp the version that wrote them, so an import can say
  where a library came from.

Both Gold Series designs are **fan recreations** measured from public reference
imagery of MrSavage's crosshair — geometry, not published settings. They are not
official presets and no endorsement is implied. This line ships in the
application and on the website next to both designs.

### Why the version test pins sources to each other, not to a literal

`tests/releaseVersion.test.ts` asserts that package.json, the lockfile root and
`APP_VERSION` **agree**, without hardcoding `1.2.0`, so the next bump needs no
edit to the test. It also asserts three things that are easy to break quietly:

- `electron-builder.yml` contains no version literal at all — both artefact
  names come from `${version}`. A hardcoded name here would keep shipping
  `…-1.2.0.exe` forever, and the website's download links would 404.
- `docs/release-notes/v${version}.md` exists, so a version cannot be bumped
  without writing its notes.
- The website's `releases.json` may **lag** the application but must never lead
  it: `latest` is compared against package.json, and every published artefact
  must carry its own version in both filename and URL, with a plausible size and
  a 64-hex digest. Advertising a build nobody can download is the failure this
  guards.

### Not verified, and not verifiable here

Stated plainly rather than implied by omission:

- **No Windows executable exists yet**, so nothing about the packaged
  application has been tested. The development sandbox cannot produce one: it
  cannot reach the release-asset CDN that serves the NSIS compiler, and a Linux
  build cannot run `rcedit`, which is what stamps the executables' icon and
  version metadata. Both artefacts must come from the `windows-release`
  workflow's `package` job on `windows-latest`.
- **No overlay, DPI or display-scaling behaviour was exercised.** There is no
  Windows, no display server and no Electron binary in this environment
  (dependencies are installed with `ELECTRON_SKIP_BINARY_DOWNLOAD=1`). OS
  scaling at 100 / 125 / 150 / 200 % is a checklist item for a real machine,
  not a claim.
- What *is* covered automatically: arc geometry against independently written
  trigonometry, identical geometry at application scale 1 / 1.25 / 1.5 / 2,
  legacy full-circle output unchanged, schema-v3 defaults and repairs, preset
  catalogue integrity, and `scaleFactor` handling against fake displays
  (including a non-finite value falling back to 1). Application *scale* is the
  crosshair setting; it is not OS display scaling, and the two are not
  conflated anywhere in this document.

## Prepared, inert: the release-publish workflow

`.github/workflows/release-publish.yml` exists to publish a release from a
packaging run's artefact, and it still carries 1.1.0-specific text. It is
**not** modified in this branch, because changing a release workflow in the same
commit as a version bump makes the release harder to read, and because the
numbers in its body must be the measured ones. When publishing, either update it
or create the release directly; the changes it would need are:

- `inputs.run_id.default` → the `windows-release` run id for tag `v1.2.0`.
- `inputs.tag.default` → `v1.2.0`.
- The body text at lines 92–98 → the release notes above, with the two artefact
  names, their measured sizes and their SHA-256 digests.

`release-assets.yml` needs no change: it attaches exactly the two executables
from the packaging run to whichever release is published, prints their sizes and
digests before upload, fails loudly rather than duplicating assets, and never
rebuilds or re-uploads anything by hand. The v1.1.0 release keeps its assets.

## Publication steps — each one needs explicit approval

Nothing below has been done.

1. **Review and merge this branch.** It changes version metadata, one provenance
   constant, one test file and documentation — no feature code.
2. **Push the tag:** `git tag v1.2.0 && git push origin v1.2.0`. This is what
   starts `windows-release.yml`: the `quality` job (tests, both typechecks,
   production build on ubuntu-latest) and then the `package` job
   (windows-latest, `electron-builder --win --publish never`).
3. **Read the measured numbers** from the packaging run's log — it prints the
   unpacked install size and, for each executable, its exact byte size and
   SHA-256 — and download the artefact `crshhx-windows-v1.2.0` to verify the
   bytes independently.
4. **Run the Windows checklist** in
   `docs/release-notes/v1.2.0-windows-verification.md` on a real machine, with
   both executables. This is the step that produces evidence the Gold Series
   works in the actual application; nothing in this sandbox can substitute
   for it.
5. **Publish the GitHub release** — tag `v1.2.0`, title
   `crshhx v1.2.0 — Gold Series`, body from the release notes above.
   `release-assets.yml` then attaches the two executables to it.
6. **Update the website** with the measured entry above, set `latest` to
   `1.2.0`, rebuild, and let the merged change deploy. Only after this does the
   download page describe the build people can actually download — which also
   closes the current gap, where the live site already describes the Gold Series
   as installed while the newest published executable predates it.
